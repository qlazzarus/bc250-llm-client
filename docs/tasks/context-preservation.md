# 최우선 컨텍스트 보존 구현 작업

실행 담당 모델: **DeepSeek 4.1 Flash**. 이 문서는 해당 모델에 한 작업씩 전달할 구현 지시서이며, 여기 나열한 기능은 아직 구현 완료로 간주하지 않는다. 모델 이름은 코딩 작업 담당을 뜻하며 클라이언트의 서비스 모델 설정을 바꾸라는 지시가 아니다.

현재 동작은 [채팅과 컨텍스트](../chat-context.md)를 따른다. 기존 strict 보존·요약 복구 기능을 유지하면서 관측 UI, 초장문 처리, 구조화 기억, 원문 재조회와 복구 UX를 추가한다. 이 문서가 다른 TODO보다 우선한다. 일반 Wiki 개선·모델 전환 확장·외부 인프라 추가는 함께 구현하지 않는다.

## 1. 확정 요구사항과 검토 제안

### 확정 요구사항

- 미요약 완료 이력을 조용히 버리지 않는다. 보존이 불가능하면 명시적으로 실패한다.
- **컨텍스트 사용량과 남은량을 막대그래프로 표시한다.** 출력 예약과 안전 여유도 구분한다.
- **압축 중임을 사용자가 알 수 있어야 한다.** 대기·처리·검증·완료·실패를 보여 준다.
- 압축 전후 입력 크기와 처리 범위는 같은 조건에서 비교 가능할 때만 표시한다.
- 이미지 프롬프트의 독립 요청, 일반/롤플레잉의 완료 이력 정책, 원문 보존을 유지한다.
- mock 검증과 실제 BC-250 모델 검증을 구분한다.

### 주요 기억 UI 리뷰

**읽기 전용으로 먼저 제공하는 것을 권장한다.** 사용자는 대화 초반의 제약이나 최신 정정이 요약에서 빠졌는지 확인할 수 있고, 원문을 찾아 수정할 근거를 얻는다. 다만 모델이 만든 요약을 사실로 확정해 보이거나 모든 기억이 이번 요청에 사용됐다고 오해하게 만드는 위험이 있다.

권장 UI는 기본 화면의 바 옆 `컨텍스트 보기` 버튼과 접이식 패널이다. 패널은 `이번 요청에 전달한 기억`과 `보관 중인 기억`을 구분하며, 목표·제약·확정 결정·미해결·최신 정정·미승인 제안으로 나눈다. 각 항목에 원문 메시지 링크와 상태를 표시한다. `모델이 작성한 요약`임을 표시하고, assistant 제안은 사용자 결정으로 보여 주지 않는다.

- 첫 버전은 조회와 원문 이동만 제공한다. 없는 원문은 링크를 조작하지 않고 `출처 확인 불가`로 표시한다.
- `중요도`를 모델의 임의 점수로 확정하지 않는다. 사용자 목표·명시 제약·확정 결정·최신 정정을 먼저 배치한다.
- 수정·삭제·고정은 예산·충돌·커서 의미를 바꾸므로 항목별 편집 기능과 분리한다. 현재 전체 요약 편집은 유지한다.
- 숨은 추론, chain-of-thought, 비밀 system 설정과 credential은 노출하지 않는다. 압축 단계는 작업 상태이며 모델의 생각 과정이 아니다.
- 좁은 화면에서는 대화 본문과 입력을 밀어내지 않도록 닫힌 패널/하단 시트를 사용한다.

**이 제안은 아직 사용자 확정 사항이 아니다.** 아래 CT13은 승인 전 구현하지 않는다. CT01~12와 CT14 이후의 필수 작업은 CT13 승인 대기와 독립적으로 진행할 수 있다. 항목별 편집·고정은 이번 실행 목록에 포함하지 않는다.

## 2. 공통 데이터·화면 계약

### 컨텍스트 바

같은 모델·epoch·요약 revision·질문·Wiki 자료·출력 설정에 대한 **하나의 입력 snapshot**을 사용한다.

```text
컨텍스트 16,384 토큰 · 실측 · 이번 요청
[ 입력 8,192       | 답변 예약 2,048 | 여유 512 | 남음 5,632 ]
입력 50.0% · 예약 포함 점유 65.6% · 추가 입력 여유 34.4%
```

`C = 모델의 유효 context 한도`, `I = 최종 입력 전체`, `O = 출력 예약`, `S = 안전 여유`로 정의한다. `remaining = max(0, C-I-O-S)`, `overflow = max(0, I+O+S-C)`다. 바의 분모는 C이며 네 구간을 구분한다. 초과 값은 바 너비를 제한해 렌더링하되 `초과 N 토큰`을 별도로 표시한다.

- 전체 I에는 system·요약·최근 원문·현재 질문·Wiki·schema·template가 포함된다. 각 부분을 따로 토큰화한 합을 실제 총 입력이라고 표시하지 않는다. 부분별 숫자가 필요하면 추정임을 별도 표시한다.
- 토큰 계수가 불가능하면 `확인 중/확인 불가`로 표시하고 0이나 100%를 만들지 않는다. 분모가 0·null이면 비율을 계산하지 않는다.
- 계수 출처는 `measured`/`estimated`/`unknown`으로 구분한다. 추정 수치는 `약`과 `추정` 표시를 사용한다.
- 전송 전 첫 화면은 `아직 계산하지 않음`, 답변 후는 `마지막 요청 기준`이다. 후속 사용자 입력까지 반영하지 않은 값을 현재 초안의 실시간 계수로 부르지 않는다.
- 답변 스트리밍으로 생성된 토큰을 O 위에 다시 더해 중복 계산하지 않는다. 다음 요청에 포함되는 답변 원문은 새 입력 snapshot에서 계산한다.
- 대화 전환·모델/epoch·출력 길이·요약 revision 변경 시 stale 표시를 하거나 재계산한다. 이전 요청 수치는 이력으로만 보여 준다.
- 사용량은 대화의 평생 누적 토큰이 아니다. 압축 뒤 감소할 수 있다. 압축률은 기억 정확도 지표가 아니다.

### 압축 상태

```text
대화 확인 → 요약 대기 → 압축 처리 → 결과 검증 → 적용 완료
                                      └ 실패 / 취소 / 시간 초과
```

기존 summary_jobs 상태값을 무조건 바꾸지 않는다. 세부 phase는 별도 필드/관측 레코드로 관리하고 저장 성공과 검증 중을 구분한다. 여러 작업을 처리하면 job ID와 단조 증가 sequence로 상태를 구분한다.

처리할 batch 수가 확정된 경우만 `2/4 묶음 완료`를 표시한다. 분모가 불명하거나 재계획 중이면 indeterminate 진행 표시를 사용한다. 경과 시간이나 토큰 생성 속도로 임의의 완료 퍼센트·남은 시간을 만들지 않는다. 재시도 횟수와 실패 이유를 표시하며 이전 정상 요약이 유지됐는지 알린다.

현재 `send_message()`는 요청 전 압축을 마친 뒤 SSE를 연다. 따라서 SSE 이벤트만 추가해서는 준비 중 UI를 만들 수 없다. CT03/04에서 **POST 응답 대기 중에도 읽을 수 있는 작업 상태 조회**를 제공한다. 일반 HTTP 응답에도 동일하게 적용한다.

### Snapshot과 출처

최소 계약 후보: `snapshot_id`, `generation_id`, `model_id`, `model_epoch`, `summary_revision`, `context_limit`, `input_tokens`, `reserved_output_tokens`, `safety_tokens`, `remaining_tokens`, `overflow_tokens`, `token_count_source`, `included_message_count`, `omitted_uncompressed_count`, `phase`, `job_id`, `sequence`, `updated_at`.

- 정상 strict 응답의 omitted_uncompressed_count는 0이다. Wiki 참고자료 제외와 원문 누락을 혼합하지 않는다.
- 요청 snapshot은 불변 이력이고 live 준비 상태는 변경 가능 상태다. 두 레코드를 덮어쓰며 혼합하지 않는다.
- 요약 원문 전체나 대화 본문을 polling 응답에 반복해서 넣지 않는다. 세부 항목/출처 조회는 별도다.
- 새 필드는 기존 클라이언트에 additive하게 제공한다. 필요한 migration 버전은 실행 시 최신 schema에서 결정한다.

## 3. DeepSeek 4.1 Flash 실행 규칙

1. 한 번에 **Task 하나만** 실행한다. 의존 작업이 끝났는지 확인하고 예상 밖 코드 차이는 먼저 보고한다.
2. 해당 Task의 파일과 직접 호출 경로를 읽고, 실패 재현/계약 테스트를 먼저 추가한다. 모듈 전체나 저장소 전체를 한 번에 재작성하지 않는다.
3. Task 대상 밖의 기능·배포·운영 데이터·서비스 모델을 변경하지 않는다. 외부 서비스나 벡터 DB를 추가하지 않는다.
4. 테스트 실패를 없애려고 strict 정책을 완화하거나 검사를 삭제·skip하지 않는다. 실모델/외부 서비스가 필요한 검사는 구분해 보고한다.
5. 완료 시 해당 체크박스와 현재 구성 문서의 관련 설명만 갱신한다. 시간순 구현 일지는 만들지 않는다.
6. 답변에 변경 파일·동작·실제 테스트 결과·남은 문제·다음 Task를 제시한다. 기존 문서의 통과 숫자를 새 결과로 재사용하지 않는다.
7. 아래 CT13만 별도 검토 제안이다. 나머지 Task는 이 문서의 승인된 구현 범위이며, 매 작업마다 다시 허가를 요청하지 않는다. 운영 배포/장애 주입은 CT20의 별도 실행 범위다.

## 4. 작업 순서

**먼저 CT01~07로 상태를 보이게 하고, CT08~12로 압축·기억 보존을 확장한다.** 이후 CT14~19로 복구·비용·원문 검색을 개선한다. CT13은 사용자 선택 시 CT12 뒤에 끼워 넣는다. CT20은 로컬 기능 완료 후 실기 검증이다.

### CT01 [ ] 컨텍스트 관측 DTO와 계산 계약

- 의존: 없음.
- 읽기: `prompting.py`, `main.py`의 prepare_chat_context/check_payload_budget/generation_dict, `frontend/src/api.ts`, `db.py`.
- 변경: 관측 모델·직렬화 계약과 `C/I/O/S` 계산 helper 및 단위 테스트. 아직 UI·요약 알고리즘을 변경하지 않는다.
- 완료: 위 snapshot 필드의 nullable/enum 의미 확정. 4k/16k, overflow, unknown, template 비가산성, stale 구분 테스트 통과.
- 검증: 관측 단위 테스트 + `tests/test_prompting.py`, `tests/test_model_context.py`.

### CT02 [ ] 생성별 예산 snapshot 저장

- 의존: CT01.
- 변경: `db.py`, 관측 repository, `main.py`의 실제 payload 계수 지점. 필요한 additive migration 하나로 변경을 제한한다.
- 완료: 실제 전송 payload와 동일한 I/O/S/model/epoch/revision을 저장하고 요청 ID로 조회한다. 압축 전후 값을 서로 덮어쓰지 않는다. 기존 generation 사용 계약을 유지한다.
- 검증: migration 반복·기존 row·실측/추정·실패 요청·모델 변경 및 strict 누락 0 테스트.

### CT03 [ ] 요청 전·후 압축 상태 게시

- 의존: CT02.
- 변경: 요약 worker와 prepare_chat_context의 상태 갱신, 최소 작업 phase 저장소. 요약 수행 자체는 유지한다.
- 완료: queued/running/validating/committed/failed/cancelled 의미를 실제 코드 경계에 연결한다. before/after 토큰 수는 동일 조건에서만 비교한다. 재시도·재시작·수동 편집 충돌에도 거짓 완료를 게시하지 않는다.
- 검증: timeout·length·검증 실패·DB commit 실패·소유 worker 경합·상태 sequence 테스트.

### CT04 [ ] 준비 상태와 snapshot 조회 API

- 의존: CT03.
- 변경: 생성 조회에 경량 context 필드 추가, 필요시 `GET /conversations/{id}/context` 조회. 기존 인증·대화 소유 범위를 그대로 적용한다.
- 완료: 클라이언트가 보낸 request_id로 POST 대기 중 상태를 읽는다. 아직 생성 row가 없는 짧은 경합은 `준비 중`으로 재조회하며 영구 404는 종료한다. SSE/일반 HTTP, 재연결과 background 압축을 지원한다.
- 검증: 두 대화/요청 구분, 삭제·404·중복 조회·응답 역순·민감한 본문 미포함 API 테스트.

### CT05 [ ] 컨텍스트 사용량 바 컴포넌트

- 의존: CT01, CT04.
- 변경: `frontend/src/api.ts`, `ContextUsageBar.tsx`, 해당 스타일·컴포넌트 테스트. 처음에는 fixture 데이터로 동작시킨다.
- 완료: 입력/출력예약/안전여유/남은량 바와 숫자·범례. unknown/stale/overflow/추정 표시. 색상만으로 구분하지 않고 screen reader용 설명을 제공한다. 320px 폭에서도 입력창을 가리지 않는다.
- 검증: 0/100%/초과/unknown/반올림/모델 변경·키보드·접근성 DOM 테스트. 실제 모델 호출 없음.

### CT06 [ ] 압축 진행 표시 컴포넌트

- 의존: CT03~04.
- 변경: `ContextCompactionStatus.tsx`, 테스트·스타일. 바와 별도 상태 컴포넌트로 둔다.
- 완료: 대기/압축/검증/적용/실패와 처리 batch, 재시도, 취소·timeout 표시. 실제 분모가 없으면 퍼센트를 표시하지 않는다. aria-live 알림을 과도하게 반복하지 않는다.
- 검증: stage 전이·재시도·새 job·역순 이벤트·변동 분모·기존 요약 유지 안내.

### CT07 [ ] 채팅 화면에 상태·바 연결

- 의존: CT05~06.
- 변경: `frontend/src/main.tsx`와 필요시 전용 polling hook. 백엔드 알고리즘을 이 Task에서 변경하지 않는다.
- 완료: POST 직후 request_id를 기준으로 준비 상태를 조회한다. 활성 대화만 제한된 주기로 polling하고 종료·화면 전환 때 정리한다. snapshot은 요청별로 맞추며 오래된 응답이 새 화면을 덮어쓰지 않는다. 입력창 초안을 보존한다.
- 검증: SSE 시작 전 압축, 일반 HTTP, 중단·재연결·대화 전환, 409/422/404, background 압축을 mock API로 연결. frontend lint/test/build.

### CT08 [ ] 초장문 턴의 안정적인 분할 계획

- 의존: CT02~03.
- 변경: 순수 분할 planner와 테스트. 아직 활성 요약 커서를 변경하지 않는다.
- 완료: 메시지 ID·문자 범위·순서·내용 해시를 가진 조각 계획. 완성된 요약 payload 기준으로 조각 예산을 확인한다. Unicode·코드·숫자·빈 조각·지나치게 큰 필수 지시를 처리하고 원문 범위가 빠지거나 중복되지 않는다.
- 검증: 한 턴이 예산 초과, 여러 메시지, Korean/emoji/code, 경계 전후 원문 재조합, 모델 context 변경.

### CT09 [ ] 조각 요약 중간 저장과 재개

- 의존: CT08.
- 변경: 조각 상태 repository/migration과 worker의 조각 실행 경로.
- 완료: 중간 결과는 비활성 상태로 저장하고 snapshot/해시/revision과 결합한다. 같은 작업 재개가 중복 원문을 적용하지 않는다. 각 조각은 stop·schema·예산 검사와 기존 시도/시간 상한을 따른다. 처리 범위를 CT03 상태에 게시한다.
- 검증: 조각 사이 강제 종료·재시작·응답 유실·수동 편집·model epoch 변경·length. 기존 요약과 활성 커서는 그대로 유지.

### CT10 [ ] 조각 병합과 커서 원자적 적용

- 의존: CT09.
- 변경: 전체 조각 검증·최종 병합·커밋 경로만 추가한다.
- 완료: 빠짐없는 연속 범위와 최신 revision을 확인한 뒤 본문·커서·작업 완료를 한 transaction으로 적용한다. 병합도 최종 payload 예산을 검사한다. 병합이 너무 크면 제한된 다단 병합 또는 명시적 실패로 처리하며 무한 반복하지 않는다.
- 검증: 누락·중복·변조 조각, 병합 timeout/length, commit 실패, 원문 미삭제와 처리 전 커서 유지.

### CT11 [ ] 구조화 기억 항목 schema와 검증기

- 의존: CT10.
- 변경: 목표/제약/결정/미해결/정정/미승인 제안 항목 schema, parser, 원문 ID/span 검증기와 테스트. 아직 프롬프트 생성 경로를 바꾸지 않는다.
- 완료: 항목 ID, 출처, 상태, 요약 revision 정의. 존재하지 않는 원문·다른 대화·삭제된 출처는 연결하지 않는다. 사용자 진술과 assistant 제안을 구분한다. 기존 자유 텍스트 요약은 출처를 만들어내지 않고 legacy 항목으로 처리한다.
- 검증: 위조 ID/span, 정정/모순, 오래된 수동 텍스트, 미승인 제안의 확정 승격 방지.

### CT12 [ ] 구조화 요약 생성·저장·입력 연결

- 의존: CT11.
- 변경: 요약 출력 계약과 저장·프롬프트 렌더러. 구조화 기억이 추가돼도 기존 텍스트 summary API 호환을 유지한다.
- 완료: 유효한 결과만 저장하며 수동 텍스트 편집 시 구조화 항목도 명시적으로 무효화/재생성 대기 처리한다. 원문 출처와 이번 요청 포함 여부를 snapshot에 묶는다. 항목은 비지시 참고자료로 전달한다.
- 검증: 기존 대화 migration, schema 실패, 반복 요약·최신 정정, summary_revision 충돌, 텍스트와 구조화 자료 불일치 방지.

### CT13 [보류: UI 제안 승인 필요] 주요 기억 조회 패널

- 의존: CT07, CT12, 사용자 범위 확정.
- 변경: 경량 항목 조회 API, `ContextMemoryPanel.tsx`와 원문 메시지 이동. 항목별 편집·삭제·고정은 제외한다.
- 완료: `이번 요청에 전달`/`보관 중` 구분, 카테고리·출처·상태·요약 작성 주체 표시. 접힌 기본 상태와 모바일 sheet, 키보드 닫기·포커스 복귀. 검색된 원문과 생성된 요약을 구분한다.
- 검증: source pagination 이동, 삭제·불명 출처, stale revision, 다른 대화 누출 없음, 미승인 제안 표시. 모델 판단을 확정 사실로 표시하지 않음.

### CT14 [ ] 요약 재시도·재생성 API

- 의존: CT10, CT12. CT13은 필수 아님.
- 변경: 명시적 action 요청 DTO와 멱등 작업 접수. 새 action에는 expected_summary_revision을 요구한다.
- 완료: 실패 작업 재시도와 원문에서 새 요약 생성의 의미를 분리한다. 정상 활성 요약은 새 결과가 검증·커밋될 때까지 유지한다. 원문과 기존 커서를 먼저 지우지 않는다. 이미지 모드 거절·동시 실행 잠금 유지.
- 검증: 중복 요청·충돌·재생성 실패/취소/재시작·기존 빈 요약 편집 호환.

### CT15 [ ] 복구 동작 UI

- 의존: CT07, CT14.
- 변경: 실패 알림의 재시도, 설정의 재생성 동작과 상태 연결.
- 완료: 각 버튼의 효과를 설명하고 진행 중 중복 접수를 막는다. 재생성이 기존 기억을 즉시 지우지 않음을 안내한다. 결과 불명은 같은 요청 ID로 조회하고 새 작업을 자동 생성하지 않는다.
- 검증: timeout·409·중복 클릭·페이지 재진입·focus·초안 보존.

### CT16 [ ] 페이지 단위 이력 읽기와 계수 비용 제한

- 의존: CT10, CT12.
- 변경: 완료 이력 조회와 planner의 페이지 처리, 계수 cache를 도입한다면 key를 model/epoch/template/payload 전체에 결합한다.
- 완료: 작은 데이터에서 동일한 포함 범위·원문 순서·요약 커서 결과를 유지한다. SQL/RSS/계수 호출을 계측하고 경계에서 누락 없이 처리한다. 파일·모델 교체 시 cache를 재사용하지 않는다.
- 검증: 큰 합성 이력, 동일 timestamp, 페이지 경계 턴, 취소/실패 혼합, epoch/revision 변경, deadline.

### CT17 [ ] 대화 원문 FTS 인덱스와 조회

- 의존: CT11, CT16.
- 변경: 대화 원문 전용 FTS5 schema/repository와 테스트. Wiki FTS를 수정하지 않는다.
- 완료: 동일 대화의 완료 원문만 검색하며 삭제와 상태 변경에 동기화한다. 결과 ID/span·순위·길이 상한을 반환한다. 검색 대상에 실패·취소·미완료·다른 대화 내용을 포함하지 않는다.
- 검증: 인덱스 재구축·migration, 특수문자 query, 한국어·숫자, 삭제와 페이지 데이터, 무관 질의.

### CT18 [ ] 검색 원문을 최종 예산에 연결

- 의존: CT12, CT17.
- 변경: 보강 필요 판단·발췌·source metadata와 최종 payload 구성.
- 완료: 최근 원문·요약과 중복을 제거하고 검색 자료 예산 상한을 둔다. 추가 자료 부족 시 검색 보강만 제외하고 strict 원문 보존은 유지한다. 이번 요청에 실제 전달한 원문을 snapshot에 기록한다.
- 검증: 오래된 수치·코드·정정 재질문, 무관한 과거 문맥, 같은 이름, prompt injection 자료, 총 예산/epoch 일치.

### CT19 [ ] 통합 품질·UI 검증과 문서 반영

- 의존: 필수 CT01~12, CT14~18. CT13은 승인된 경우만 포함.
- 변경: 통합 테스트와 현재 구성 문서. 새 기능을 추가하지 않는다.
- 완료: 11턴/20메시지, 6턴 이하 장문, 단일 초장문, 요약+Wiki+긴 출력, length/timeout/반복 실패, 수동 편집, epoch 변경, 재시작, 동시 생성, 실패/취소 혼합, 이미지 독립 동작을 검증한다. 바의 숫자·상태가 backend snapshot과 일치한다.
- 검증: 전체 backend 회귀, frontend lint/test/build, 실제 브라우저 모바일/키보드. 합성 대화의 목표·제약·수치·정정 보존은 원문 정답과 비교하며 압축률과 분리한다.

### CT20 [ ] BC-250 실모델 검증

- 의존: CT19, 운영 테스트 범위·배포 창 확정.

- 검증: 비민감 테스트 대화, 데이터 보존/정리 결정, 실패 시 복구. mock 통과를 실제 모델 통과로 표현하지 않는다.

## 5. 실행용 프롬프트

DeepSeek 4.1 Flash 세션에서 아래 내용을 붙여 넣고 `CT01`을 실행할 Task로 바꾼다. 모델을 이 문서 자체가 전환하지는 않는다.

```text
이 저장소의 docs/tasks/context-preservation.md를 읽고 CT01만 구현해줘.
실제 코드와 문서가 다르면 코드를 우선하고 차이를 보고해줘.
선행 Task 완료를 확인한 후 필요한 파일과 직접 호출 경로만 읽어줘.
실패 재현/계약 테스트를 먼저 만들고 해당 Task 범위만 최소 변경해줘.
strict 보존, 원문 보존, epoch/revision 검증, 기존 API 호환을 유지해줘.
관측 수치가 없으면 임의 퍼센트를 만들지 말고 unknown으로 표시해줘.
CT13은 사용자 승인 전 구현하지 마. 이번 Task 외 작업·배포는 수행하지 마.
완료 시 실제 테스트 결과와 변경 파일, 남은 문제, 다음 Task를 알려줘.
현재 구성 설명에는 구현된 최종 동작만 쓰고 이 문서에 실행 일지를 쌓지 마.
```

## 6. 검증 명령 기준

```sh
PYTHONPATH=. APP_API_KEY=client-key LLM_GATE_API_KEY=gate-key .venv/bin/python -m pytest tests/test_context_preservation.py tests/test_prompting.py tests/test_model_context.py tests/test_summary_model_budget.py -q
npm --prefix frontend run lint
npm --prefix frontend test -- --maxWorkers=1 --testTimeout=15000
npm --prefix frontend run build
```

Task별 새 테스트를 위 명령에 추가한다. API·저장소 변경은 관련 API/migration 테스트까지 검사하고 CT19에서 전체 회귀를 수행한다. Unix 소켓·별도 Studio checkout·실제 GPU가 필요한 테스트는 환경 요구를 구분한다.
