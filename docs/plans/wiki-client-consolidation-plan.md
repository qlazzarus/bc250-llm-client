# 공유 Wiki의 LLM Client 통합 실행 계획

작성일: 2026-11-13. 상태: **통합 설계 및 전환 계약 참고 문서**. Task 상태와 실행 순서는 [Wiki·기억 실행 계획](wiki-memory-execution-plan.md)의 I00~I10에서 관리한다.

> 아래 ‘현재 확인 사실’은 통합 설계 당시의 소스 조사 기록이다. 작업 공간에는 이후 I01~I08 구현이 추가됐으며, 운영 반영 여부나 운영의 유효 설정을 의미하지 않는다. 2026-11-13 I09의 최신 운영 읽기 전용 조사와 전환 차단 조건은 [실행 계획의 I09](wiki-memory-execution-plan.md#i09-진행-중-운영-전환-준비와-리허설)를 따른다.

## 방향과 현재 확인 사실

Wiki는 가족용 LLM 사용자가 함께 보는 **공유 지식 공간**이다. Client에 접근하는 사람은 같은 문서와 공유 기억을 보고 편집할 수 있다. 이는 공통 설정과 가족이 공유하기로 한 정보를 함께 활용하는 장점이다. 현재 개별 사용자 인증·개인 기억·개별 접근 제어는 제공하지 않으며 기존 후속 TODO로 유지한다. 사용자를 식별할 수 없는 `나`에 관한 자동 개인 기억은 보류한다. 공유 UI에서도 데이터가 앱 접근자에게 공유됨을 분명히 알린다.

목표 구성: React Wiki 관리 화면 → 기존 Client FastAPI 인증 API → Client 내부 Wiki repository → 기존 Client SQLite의 Wiki 문서·FTS·Alias·기억/작업 테이블. 대화 RAG·자동 기억도 동일 repository를 사용하며 LLM 요청은 기존 gate와 예산을 따른다. 별도 Wiki 서비스·DB 파일·상주 모델·벡터 DB는 추가하지 않는다.

- 현재 별도 Wiki 소스는 [읽기 전용 스냅샷](../../tests/fixtures/wiki_server_w12/main.py)으로 확보했다. 문서 CRUD, FTS5 `unicode61`, 부분 문자열 검색, FTS trigger와 `/api/ask`가 있다. 검색은 토큰 최대 12개를 OR로 결합하고 FTS 오류를 삼킨다. 확보 당시 파일의 SHA-256은 `20889a43f3f749854ef9beace60a31fb18c96afb34b782120f2e9d4a07c19953`; 운영 중인 프로세스의 실제 코드와 일치한다고 가정하지 않는다.
- 현재 Client의 [main.py](../../backend/app/main.py)는 `/api/v1/wiki/documents` CRUD를 별도 Wiki로 전달하고 RAG/기억 작업도 HTTP를 사용한다. [wiki.py](../../backend/app/wiki.py)는 그 어댑터다. Client UI에는 검색·자동 기억 토글과 이력은 있으나 문서 관리 화면은 없다.
- 기존 별도 Wiki HTML을 읽기 전용으로 확인한 기능은 문서 목록·생성·편집·삭제·검색 및 AI 질문이다. UI 코드는 현재 스냅샷에 포함되지 않는다. 동작을 참조해 Client React UI를 작성하며 `/api/ask`의 LLM 직접 호출은 이전하지 않는다.
- 사용자는 기존 **별도 Wiki DB 문서**를 버리고 빈 공유 Wiki로 시작해도 된다고 했다. Client DB의 대화·메시지·작업 기록과 기존 공유 기억 메타데이터를 삭제해도 된다는 의미는 아니다. 새 저장소는 빈 문서에서 시작하며 별도 Wiki에서 자동 import하지 않는다. 삭제·서비스 종료·운영 migration·배포는 이번 계획 작성에서 실행하지 않는다.

## 전환 안전 계약

1. 현재 운영은 구형 Wiki HTTP writer가 실제 쓰기를 수행한다. 구현 중에는 운영 경로를 임의로 끊지 않는다. 통합 기능은 기본 비활성·격리 테스트부터 시작하고, 전환 시 구형 자동 writer와 수동 Wiki 쓰기를 중단한 뒤 통합 writer 하나만 켠다. 사용자에게 전환 중 쓰기 불가를 표시한다.
2. 새 통합 문서의 ID는 기존 외부 Wiki ID와 별도 namespace다. 과거 `wiki_memory_jobs.document_id`, W09 `memory_records.wiki_document_id`, quarantine 및 저장된 출처의 숫자만으로 새 문서를 가리키거나 소유권을 추정하지 않는다. migration에서 저장소 식별자를 명시하고 기존 데이터는 `legacy_external`로 보존한다. 기존 이력의 문서 열기·수정·삭제·RAG·정정 연결을 차단하거나 옛 자료로 표시한다. 새 문서는 `integrated`만 참조한다. FK·unique·쿼리 및 격리도 `(store_id, document_id)` 기준으로 설계하며 외부 ID=통합 ID 충돌과 없는 옛 ID를 검증한다. 기존 active/pending/unknown은 이력 보존과 안전한 격리 정책을 적용하고 통합 active로 자동 승격·재전송하지 않는다. 이전 버전이 이 새 저장소 식별자를 무시하는 경우 자동 롤백 writer 활성화를 금지한다.
3. 같은 SQLite의 문서 변경, FTS trigger, 활성 기억 전환, 작업 결과 기록은 **한 연결·한 트랜잭션**에서 처리한다. 실패하면 모두 rollback한다. 사용자 질문·LLM 추론·화면 확인·HTTP await 동안 DB 트랜잭션을 보유하지 않는다.
4. revision은 서버가 관리하는 단조 증가 정수 등 충돌 없는 값으로 구현하고 조건부 UPDATE와 결과 확인을 원자적으로 수행한다. UI·자동 기억은 사용자 또는 자동 작업이 읽은 revision을 제시한다. 두 요청이 같은 revision을 수정하면 하나만 성공하고 다른 하나는 409다. 개별 사용자의 명시적 승인도 레코드·revision·후보 값·출처에 결합하고 적용 직전 재검증한다.
5. 작업 ID와 payload hash는 같은 트랜잭션에 기록한다. 같은 ID/같은 payload 재조회는 결과를 반환하며 다른 payload는 충돌이다. commit 전후 종료·응답 유실·재시작 시 안전한 결과 조회를 제공한다. Wiki 저장소가 내부화돼도 UI나 HTTP 호출 측 응답 유실은 가능하므로 성공 여부를 추정하지 않는다.
6. 출처 삭제 redaction, 비활성·격리 기억 필터, 일반 Wiki와 기억 채널 분리 및 Alias 검색의 공통 필터는 기존 W08/W15 정책을 유지한다. 초기 자동 기억은 승인된 네 공유 속성만 지원한다. 모호함·충돌은 보류하고 UI의 확인 정책은 후속 I07에서 구현한다.
7. Family Wiki 문서를 버릴 수 있다는 결정은 **즉시 운영 삭제 승인이나 Client DB 초기화 지시가 아니다**. 운영 전환 시 Wiki DB의 보존 여부·백업·삭제 시점과 복구 가능 기간을 전환 절차에 명시한다. 새 Wiki 시작 후 생성된 문서가 있는데 예전 서비스로 전환하면 그 문서가 사라진 것처럼 보이므로, 롤백은 우선 통합 쓰기 중단과 읽기 전용 복구다. 구 서비스 재개는 양쪽 변경 처리·이력 충돌을 확인한 명시적인 별도 복구 절차로만 수행한다.
8. W11 HTTP 경로는 전환기 레거시 호환용이다. 새 내부 repository의 오류를 빈 검색으로 바꾸지 않는다. 기존 `/api/v1/wiki/documents`와 기존 성공 응답 모양은 유지하며 새 검색·revision은 하위 호환되는 추가 또는 opt-in 계약으로 제공한다. 외부 포트 8020/API 사용 여부는 전환 전 확인하고 미확인 호출자가 있다면 종료하지 않는다.

I00~I10의 의존성·수정 대상·완료 조건·테스트 및 현재 상태는 [통합 작업 목록](wiki-memory-execution-plan.md#3차-가족-공유-wiki-통합--다음-작업부터-순서대로-실행)을 따른다. 이 문서는 전환 안전 계약과 설계의 참고 자료로 유지한다.

## W12~W19 및 검색 계획과의 관계

- 기존 W12의 [별도 서버 패치](../patches/wiki-server-w12.patch)는 **미적용 참고 자료**로만 둔다. I03의 내부 revision 구현과 동시성 테스트에 아이디어를 재사용할 수 있으나 패치 자체가 통합 구현은 아니다.
- 기존 W13의 별도 서버 operation API는 I07의 동일 DB 트랜잭션·작업 결과 조회로 대체한다. 기존 W14는 I07로 대체한다. W15/Q 작업은 I06, W16~W19는 I08에 연계한다. 완료 이력 W00~W11은 보존한다.
- [Alias 계획](wiki-query-alias-plan.md)의 A01~A09 및 정규화·충돌 규칙은 유효하다. 외부 Wiki에 수정사항을 배포한다는 전제와 서버 소스 미확보 가정은 폐기하고 Client repository·기존 DB에서 구현한다. 빈 Wiki로 시작하므로 `bc250 ai 서버`와 Alias가 자동 존재하지 않는다. 사용자 문서 생성 및 명시적 Alias 등록 후 네 표기가 같은 문서를 검색해야 한다.

## 위험과 롤백

| 위험 | 방지·검증 | 롤백 |
| --- | --- | --- |
| 옛 문서 ID가 새 문서를 가리킴 | 저장소 namespace와 ID 충돌 테스트 | 양쪽 쓰기 중지, 옛 참조는 이력으로만 표시 |
| 두 writer 동시 활성화 | 전환 중 양쪽 쓰기 중지 후 하나만 활성화, 상태 확인 | 새 writer 비활성, 구 writer 자동 재개 금지 |
| Client DB migration/트랜잭션 실패 | additive migration, 임시 DB 반복·rollback·FTS 검증 | 쓰기 비활성 후 호환 버전 복귀. 전체 DB 복원은 별도 사고 복구 판단 |
| 전환 후 데이터 유실 | 사용자 승인된 범위만 빈 Wiki로 시작, 전환 전 백업과 전환 후 생성 자료 구분 | 읽기 전용 보존 후 자료 합치기/구 서비스 재개 방안 별도 결정 |
| 가족 공유 범위 오해 | 화면에 공유 공간 명시, 개인 식별 추정 금지 | 자동 기억 비활성·해당 내용 보류, 개인 기억 별도 설계 |
| 구형 자동 저장의 불안전 fallback | 새 저장 경로 검증 전 통합 writer 비활성, 전환 후 구 writer 비활성 | 기능 중단 상태 유지; 기존 위험 경로로 자동 복귀하지 않음 |

이번 문서 작업에서 코드·DB·운영 파일·서버 설정을 변경하거나 테스트·배포·재시작·삭제를 실행하지 않았다.
