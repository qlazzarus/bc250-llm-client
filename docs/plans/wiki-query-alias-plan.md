## 2. FTS5 토큰화 확인 기준

아래는 운영 설정이 아니라 **기본 unicode61을 쓸 경우의 예상**이다. 공백과 구두점은 경계이며 대소문자를 구분하지 않는다. 공백으로 나열한 MATCH 구문은 암묵적 AND가 된다. [SQLite 공식 FTS5 문서](https://www.sqlite.org/fts5.html#unicode61_tokenizer), [쿼리 문법](https://www.sqlite.org/fts5.html#full_text_query_syntax).

| 입력 | 기본 unicode61 예상 토큰 | 주의 |
| --- | --- | --- |
| `bc250` | `bc250` | 단일 토큰 |
| `bc-250` | `bc`, `250` | 하이픈을 tokenchars로 설정했다면 달라짐 |
| `BC 250` | `bc`, `250` | `bc250`와 자동 동의어가 되지 않음 |
| `bc250 ai 서버` | `bc250`, `ai`, `서버` | `서버가`와 동일 토큰이라고 가정하지 않음 |

원문을 SQL parameter로 바인딩하는 것과 MATCH 문법을 안전하게 만드는 것은 별개다. 쿼리 생성기가 토큰을 따옴표로 감싸고 내부 따옴표를 escape하며, 사용자 `OR`, `NOT`, `*`, `:`, `-`를 연산자로 실행하지 않도록 설계한다. 원문 `bc-250`을 그대로 MATCH에 넣는 방식은 피한다. 실제 tokenizer·phrase/AND 동작은 후속 격리 DB 테스트에서 확인한다. 이번에는 DB를 만들거나 테스트 데이터를 저장하지 않았다.

## 3. 정규화와 Alias 정책

1. 표시 제목·본문·기존 ID는 그대로 둔다. 검색용 key만 NFKC → casefold → 양끝/연속 공백 정리한다. 원문 q와 정규화 버전을 별도 보존한다. 이 규칙을 기억 fingerprint나 원문 span에 재사용하지 않는다.
2. 전역적인 하이픈/공백 삭제는 금지한다. 명시적 BC-250 표기 그룹만 `bc250`, `bc-250`, `bc 250` → `bc250`으로 매핑한다. `xbc250`, `bc2500`, `bc 2500`, `bc25`는 매칭하지 않는다. Unicode 하이픈 확장은 승인된 문자 목록과 경계 테스트가 있을 때만 추가한다.
3. 제목 전체의 정규화 key와 문서별 명시적 Alias를 별개로 관리한다. 제목이 `bc250 ai 서버`라는 이유만으로 짧은 `bc250`를 자동 등록하지 않는다. 담당자가 기존 문서의 실제 ID를 확인한 뒤 이 문서에 `bc250` 표기 그룹을 연결하는 후속 작업을 계획한다. 임의 ID 하드코딩 금지.
4. Alias 충돌은 허용·표시하고 전체 후보를 비교한다. 같은 Alias가 서버 소개와 하드웨어 문서를 가리키면 한 문서로 임의 확정하지 않는다. 현재 질문의 수식어로 순위를 정하고, 부족하면 사용자에게 대상 구분을 요청한다.
5. 저장 위치는 기존 Wiki Alias/메타데이터 기능을 먼저 확인한다. 없다면 영속적인 문서별 Alias와 인덱스 조회를 위해 **기존 Wiki SQLite 안의 보조 테이블**을 검토한다. 최소 필드는 document_id, alias_original, alias_key, normalization_version; `(alias_key, document_id)` unique와 alias_key 인덱스. 새 DB 파일·서비스는 불필요하다. 스키마 확정·마이그레이션은 별도 구현 단계다.
6. 질문의 끝부분에 있는 제한된 표현(`뭐야?`, `무엇인가요?`)과 Alias 바로 뒤 조사(`은/는/이/가`)만 경계 규칙으로 분리한다. 일반 한국어 단어 끝 글자를 무조건 자르지 않는다. `bc250 이 뭐야?` → entity `bc250`, intent `definition`; `bc250 ai 서버가 뭐야?` → title key `bc250 ai 서버`.
7. `bc250 백업 경로`에서는 `백업 경로`를 버리지 않는다. 현재 질문에 명시적 대상이 있으면 이전 발언을 섞지 않는다. 대상 없는 `그 경로는?` 같은 후속 질문만 직전 user의 제한된 주제어를 보조 입력으로 사용한다. assistant 발언은 검색 대상 확정 근거로 쓰지 않는다.

## 4. 검색 단계와 성능 제한

한 번의 Wiki 검색 요청 내부에서 다음 순서를 실행하는 것을 목표로 한다. Client가 동일 정규화를 중복 구현하거나 매 단계 HTTP 요청을 보내지 않는다.

1. **Alias/제목 key 정확 일치**: 추출한 대상 전체로 인덱스 lookup. 단일 대상 정의 질문에서 유일한 일치가 있으면 해당 문서를 우선 반환하고 종료 가능. 수식어·복수 대상·충돌이 있으면 후보만 확보하고 다음 단계로 진행한다.
2. **FTS5**: 기존 인덱스·ranking을 유지하고 안전한 검색어로 조회한다. 기존 성공 질의의 후보/순위는 비교 기준으로 보존한다. Alias 대상과 수식어 일치를 함께 평가하며 Alias 일치라는 이유만으로 무관한 본문을 답변 근거로 삼지 않는다.
3. **제한된 확장**: 앞 단계가 비었거나 필요한 관련 후보가 부족할 때만 명시적 표기 그룹·Alias의 정식 제목으로 확장한다. 최초 제안은 기본 FTS 1회 + 확장 최대 2회, 합친 후보 최대 20개, 반환 최대 3개(RAG)/5개(기억 기존 계약)다. SQL LIMIT·안전한 입력 길이/토큰 제한을 적용한다. 초과는 진단에 truncation을 표시한다.

단계 간 문서 ID로 중복 제거하고 동률 순서는 안정적으로 정한다. 서로 다른 검색기의 raw score를 그대로 합산하지 않는다. 전체 기존 8초 HTTP 예산을 늘리지 않으며 확장이 그 안에서 끝나도록 서버 시간 예산을 둔다. 확장 전용 에러는 이미 얻은 정상 결과와 함께 degraded 상태로 구분하고 전체 검색 오류를 빈 결과로 숨기지 않는다.

광범위 substring/모든 단어 OR/무제한 재시도/새 LLM/벡터 DB/새 상주 모델은 추가하지 않는다. 문서 지시를 쿼리 확장 규칙으로 실행하지 않는다. W15의 기억 문서 격리·접근 범위 필터는 **모든 단계와 최종 선택**에 동일하게 적용한다. Alias 경로로 격리 문서가 우회 유입되면 실패다.

## 5. 기존 문서·인덱스·API 호환

- 기존 제목·본문·ID·FTS tokenizer를 변경하거나 기존 인덱스를 교체하지 않는다. 검색 정규화만으로 해결 가능한지 우선 평가한다.
- Alias 보조 데이터/인덱스가 필요하면 후속 승인된 마이그레이션에서 추가만 한다. 기존 문서의 제목 key 파생은 원문 변경과 구분하고 개수/충돌 검증 후 활성화한다. 기존 CRUD와 같은 transaction에서 Alias/제목 key를 갱신하며 실패하면 함께 rollback한다. 외부 편집 경로·삭제 시 orphan 방지도 확인한다.
- 구형 `/api/search?q=&limit=` 기본 응답 list는 유지한다. 신규 `view=diagnostic` 등 명시적 opt-in에서만 envelope를 반환하도록 W11과 계약 확정한다. 미지원 서버에 대한 형식 협상과 기존 list fallback을 테스트한다. 오류나 무관 결과를 성공으로 변환하지 않는다.
- 신규 응답 예시 필드: `query.normalized`, `query.normalization_version`, `query.strategy_version`, `query.truncated`, `results[{document_id,title,revision,match_stage,matched_alias,rank}]`, `diagnostics{expanded_queries,degraded,elapsed_ms}`. 원문 질문·이전 대화가 일반 서버 로그에 무조건 남지 않도록 진단은 opt-in/길이 제한한다.

W16 답변 메타데이터는 검색 API와 구분한다:

| 필드 | 의미·검증 |
| --- | --- |
| retrieved | 검색된 후보 ID·당시 버전·검색 단계. 답변 근거라는 주장 아님 |
| provided | 최종 LLM payload에 실제 포함한 문서·발췌·버전. 예산 때문에 빠진 후보는 제외 |
| cited | 답변에서 명시한 문서 ID를 provided 집합과 대조한 결과. 임의/미전달 ID는 invalid citation |
| evidence_status | `citation_only` 또는 `unverified` 등 지원 범위를 명시. ID 일치만으로 문서가 해당 주장을 뒷받침한다고 표시하지 않음 |

실제 모델 내부의 사용 여부는 증명할 수 없다. 인용이 있어도 주장과 발췌의 일치 여부는 평가 대상이다. 새 LLM 검증 호출은 추가하지 않는다. 생성 시점 snapshot과 최종 답변 기준으로 stream/nonstream/재조회 일관성을 지키며 기존 답변 본문은 재작성하지 않는다.

## 7. 회귀·수용 기준

기준 fixture: 기존 형태의 문서 D=`bc250 ai 서버`, 본문에 소개/운영체제; D에 명시 Alias `bc250` 그룹 등록. 숫자 유사 문서·백업 문서·다른 문서에 같은 Alias를 등록한 충돌 fixture를 각각 분리한다. 이번에는 fixture를 저장하지 않는다.

| ID | 질의/조건 | 기대 |
| --- | --- | --- |
| A01 | `bc250`, `bc-250`, `BC 250`, `bc250 ai 서버` | 비충돌 fixture에서 모두 동일 ID D가 Top1, 중복 반환 없음 |
| A02 | `bc250 이 뭐야?`, `bc250 ai 서버가 뭐야?`, `BC 250은 무엇인가요?` | D Top1, 의문/조사 토큰으로 누락되지 않음 |
| A03 | 이전 대화가 휴대폰인 상태에서 A02; `그 서버는?` 후속 질문 | 명시 대상에는 이전 주제 혼입 없음; 후속은 제한된 문맥 사용, 불명확하면 임의 확정 금지 |
| A04 | `bc2500`, `xbc250`, `bc25`, `BC 2500`, 일반 한국어 고유명사 | Alias 오일치·무차별 조사 제거 없음 |
| A05 | `bc250 백업 경로`, `bc250과 다른 서버 비교` | 수식어/복수 대상 보존; 소개 문서만으로 없는 경로를 주장하지 않음 |
| A06 | 공백/대소문자/전각 변형, 따옴표/콜론/괄호/OR/NOT/*/하이픈, 긴 입력 | 결정적 정규화, MATCH 구문 주입/500/무제한 확장 없음 |
| A07 | Alias 두 문서 충돌, 제목 변경, 삭제, 인덱스 갱신 실패 | 임의 단일 확정 없음; 원자성·일관성·기존 문서 보존 |
| A08 | 정확 일치 없음, FTS만 성공, 확장만 성공, 모두 없음, 서버 오류 | 단계 순서/상한·빈 결과/오류 구분. 기존 성공 결과 회귀 없음 |
| A09 | 격리/비활성 문서 Alias, 발췌 미전달, 문서 ID 위조 인용 | 검색 필터 우회·근거 오표시 없음 |

고정 평가 집합에서 기존 성공 질의의 Recall@3를 떨어뜨리지 않고 무관 문서 비율을 늘리지 않는 것을 통과 기준으로 삼는다. A01/A02는 별도로 100% 통과해야 한다. 향상된 평균이 기존 성공 사례의 실패를 가리지 않도록 질의별 결과도 비교한다. 검색과 발췌 적합도, 답변 근거 일치율은 별도 측정한다.

성능 제안 기준: 같은 장비·데이터·동시성에서 cold/warm을 나눠 p50/p95, SQL 호출 수, RSS, 오류율 기록. 기존 성공 질의의 p95 증가는 `max(기준 p95의 10%, 5ms)` 이내를 초기 예산으로 사용한다. 측정 오차가 크면 반복 측정하고 기준을 사후 완화해 통과시키지 않는다. 제한 확장은 별도 집계하고 전체 8초 timeout 유지. 실제 수치는 **미측정**이며 기존 성능 유지가 이미 검증됐다는 뜻이 아니다.

## 8. 위험과 롤백

- Alias 오등록/충돌: 자동 제목 축약 등록 금지, 등록 전 ID 확인, 충돌 테스트. 잘못된 Alias만 비활성화하고 원문은 보존한다.
- 과도한 정규화: 범용 공백/하이픈 제거 금지, 규칙 버전별 테스트. 기능 스위치로 새 검색 전략을 끄고 기존 검색 경로로 복귀한다.
- 인덱스/CRUD 불일치: 같은 transaction·격리 테스트로 검증. 추가 구조를 남긴 채 구형 경로로 복귀하며 기존 FTS drop/rebuild를 롤백 수단으로 쓰지 않는다.
- 지연·정확도 저하: 확장 단계만 먼저 비활성화할 수 있게 한다. 질의별 회귀가 남으면 활성화하지 않는다.
- 응답 호환: 신규 envelope/근거 메타데이터 opt-in만 끄고 구형 list·본문 계약 유지. 기존 답변/문서 자동 수정 없음.

이번 검증은 소스·문서 읽기와 계획 검토만 수행했다. 운영 검색 재현, 서버 소스 확보, FTS token 실험, 인덱스 생성, 마이그레이션, 테스트 실행, 서비스 재시작 및 배포는 수행하지 않았다.
