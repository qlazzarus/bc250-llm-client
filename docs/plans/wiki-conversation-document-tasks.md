# 대화 자료의 공유 Wiki 문서 저장 실행 계획

상태: D00~D09 완료, D10은 추가 통합 검증 계획이다. D05는 사용자 요청으로 완료 처리했으며 미검증 항목은 아래 기록에 남긴다. 구현 상태와 운영 검증은 실행 기록을 따른다. 기존 통합 전환 이력과 운영 상태는 [Wiki 기억 실행 계획](wiki-memory-execution-plan.md)을 따른다. I09/I10의 실제 운영 검증은 별도로 기록한다.

## 목표와 확인된 현황

대화에서 사용자가 긴 자료를 제공하면 공유 Wiki 문서 후보를 제시하고, 사용자가 제목·본문·출처를 검토하고 저장을 확정할 수 있게 한다. 기존 단일 속성 자동 기억은 유지한다. 신규 상주 모델·서비스·벡터 DB는 도입하지 않는다.

- 운영에서 관찰: BC-250 설명 본문 안의 ‘Wiki에 저장’이라는 문구가 명시 요청으로 판정되었고, 고정 속성 추출에 실패했다. 이 작업의 실제 사용자 의도와 자료 내 인용 문구를 구별해야 한다.
- 현재 코드: `backend/app/wiki_memory.py`는 발언 내부 정규식으로 명시 요청을 판정한다. `backend/app/memory_dedup.py`는 전체 메시지 800자 이하의 제한된 공유 속성만 매핑한다. `backend/app/integrated_memory.py`의 관리 기억 문서는 일반 Wiki 검색에서 격리된다.
- 일반 문서는 최대 100,000자이고 대화 메시지는 최대 12,000자다. 기존 제한을 변경하지 않는다. 검색 색인 가능 여부와 긴 자료의 관련 발췌가 LLM에 제공되는지는 별도로 검증한다.
- 범위: 사용자가 공유를 확인한 문서는 일반 Wiki 문서로 저장하며 검색·revision 이력을 이용한다. 자동 기억 슬롯에는 넣지 않는다. Wiki 문서는 가족 공유이고 개인별 접근 제어는 범위 밖이다. 문서에 개인정보 또는 민감한 내용이 있는지 사용자가 미리보기에서 판단한다.

## 고정 정책과 UX

1. 사용자가 보낸 긴 메시지는 규칙 기반으로 문서 후보를 제시한다. 후보는 저장이 아니며, 표시 조건·최소 길이는 D00에서 실제 사례와 회귀를 보고 확정한다. 매 발언마다 무조건 팝업을 띄우지 않는다. 문서 후보는 기존 자동 기억 스위치 상태와 별도로, 메시지에서 명시적으로 여는 동작도 제공한다.
2. 미리보기에서 공유 범위, 제목, 편집 가능한 원문과 선택적 출처를 보여 준다. 원문 기본값은 선택한 **사용자 메시지**이며 LLM 답변이나 외부 자료의 사실성을 검증했다고 표시하지 않는다. 어시스턴트 답변 선택·파일 업로드·개인 기억은 범위 밖이다. 출처 미입력도 허용하며 입력된 출처가 자동 검증된 것으로 표시하지 않는다.
3. 본문 안의 ‘위키에 저장’ 같은 간접·인용 표현을 저장 지시로 판정하지 않는다. 후보 제시와 저장 의사는 구분하고, 모든 신규 문서 저장에는 사용자의 명시적 확인을 요구한다. 추출 판단은 보수적으로 하고 모호하면 조용히 저장하지 않는다.
4. 중복 후보는 기존 일반 Wiki 문서의 정확한 제목과 정규화 제목을 우선 표시한다. 유사 검색은 참고로만 표시하고 중복 부재의 증거로 취급하지 않는다. 사용자는 기존 문서 비교 후 신규 문서 생성 또는 기존 문서 편집을 선택한다. 기존 문서는 자동으로 덮어쓰지 않으며 갱신은 기존 revision 조건과 충돌 UI를 사용한다.
5. 같은 저장 요청의 재전송은 중복 문서를 만들지 않아야 한다. 요청 ID·사용자 입력 해시와 결과 기록을 문서 쓰기와 동일 트랜잭션으로 묶는 방안을 우선 검증한다. 기존 구조만으로 재시도·응답 유실을 안전하게 처리할 수 없다면 Client의 기존 SQLite에 최소 migration을 추가한다. 새 DB나 서비스는 추가하지 않는다. 취소·저장 전에는 Wiki 문서를 만들지 않는다.
6. Wiki 문서는 외부 입력이다. 문서 본문의 명령을 시스템 지시로 실행하지 않는다. 가져온 자료·검색된 자료·실제 답변에 제공된 근거를 구분하고, citation 일치만으로 내용의 진실성을 보증하지 않는다.
7. 모바일에서도 본문 편집 및 저장·취소가 가능해야 하며, 저장 성공·실패·충돌·결과 불명을 구분한다. 원문은 기본 상태 요약에 반복 노출하지 않는다. 기존 API와 기억 작업 이력, 수동 Wiki 편집, legacy 모드의 동작을 보존한다.

## D00 [x] 계약과 범위 확정

- 대상: 이 문서, `backend/app/wiki_memory.py`, `backend/app/memory_dedup.py`, `backend/app/wiki_repository.py`, `frontend/src/components/MessageList.tsx`, 관련 테스트.
- 의존성: 없음. 운영 배포와 무관하게 로컬 진행 가능.
- 작업: 현재 사용자 메시지·작업 처리·삭제와 Wiki CRUD 경계를 추적한다. 실제 사례에서 자료 안의 요청 문구, 독립된 저장 지시, 코드·인용·질문을 구분하는 예제를 정한다. 후보 길이·빈도, 제목 기본값, 출처 입력 및 저장 완료 표시를 명시한다. 애매한 표현에서 자동 저장하지 않는다.
- 완료: 후보 판정·저장 승인·원문 선택·중복·삭제·한도·재시도 계약과 대표 예제 10개 이상 기록. LLM으로 생성한 정보를 사실로 승인하지 않는다.
- 테스트: 기존 실패 사례 재현과 인용·혼합 언어·짧은 사실·질문·일반 대화에 대한 격리 단위 테스트 설계. 프로덕션 DB 사용 금지.

### D00에서 확정한 계약

- **경계 확인:** `MessageCreate.content`는 1~12,000자이며, 대화 메시지는 `user`/`assistant` 역할과 대화 ID로 저장된다. 현재 메시지 삭제 API는 없고 대화 삭제는 대화·메시지·기억 작업 이력을 cascade 삭제한다. 삭제 전에 공유 기억 출처는 별도 정리된다. 일반 Wiki 문서는 대화와 독립적이라 대화 삭제로 삭제되지 않는다.
- **기억과 Wiki 문서의 분리:** 현재 자동 기억은 응답 완료 뒤 일반 `quick` 모드에서 설정 또는 정규식상 명시 요청이 있을 때만 별도의 기억 작업으로 큐에 들어간다. 그 정규식은 발언 전체를 검색하므로 긴 인용 자료 속 문구도 잡을 수 있다. 새 문서 후보는 이 판정·스위치와 독립이며 자동 기억 슬롯을 사용하지 않는다.
- **후보 표시:** 메시지 본문을 앞뒤 공백 제거한 뒤 길이가 **1,000자 이상**이면 그 사용자 메시지에 비차단 인라인 후보를 한 번 표시한다. 모달·토스트를 자동으로 열지 않으며 후보 표시는 초안 생성이나 저장이 아니다. **모든 사용자 메시지**에는 별도 수동 진입점을 제공한다. 자동 기억 설정 상태, Wiki 저장 표현의 존재, 문장 의미만으로 저장 의사를 추론하지 않는다. 장문 코드·인용·질문도 길이만으로 후보가 될 수 있지만, 이를 명령이나 사실로 해석하지 않고 사용자가 취소·편집할 수 있다.
- **초안과 원문:** 원문 기본값은 선택한 동일 대화의 `user` 메시지 전체이며 어시스턴트 메시지, 다른 대화의 메시지, 첨부 파일은 원문으로 허용하지 않는다. 초안은 브라우저 메모리에서만 유지하고 새로고침 시 복구를 보장하지 않는다. 편집 중 대화 전환·닫기에는 변경 손실을 알리고 확인을 요구한다. 저장 직전 원본 메시지가 없어졌거나 `user` 메시지가 아니면 저장을 거절한다.
- **제목·출처:** 기본 제목은 원문의 첫 비어 있지 않은 줄을 공백 정리해 최대 200자로 자른 값이며, 해당 줄이 없으면 `대화 자료`를 사용한다. 제목은 사용자가 편집할 수 있다. 문서 category 기본값은 `general`이다. 출처는 선택 입력이고 비어 있어도 저장할 수 있으며, 입력값은 사용자가 제공한 출처로만 표시하고 자동 검증·사실성 보증으로 표현하지 않는다.
- **저장·중복:** 새 문서 저장 전 미리보기에서 공유 Wiki 범위, 편집된 제목·본문, 선택적 출처를 확인한다. 미리보기 열기·후보 수락만으로 쓰지 않으며, 최종 저장 버튼을 사용자가 눌러야 한다. 정확한 제목과 기존 제목 정규화 일치는 먼저 보여 주되 기존 문서를 자동 갱신하지 않는다. 유사 검색은 참고일 뿐 중복 없음의 증거가 아니다. 기존 문서 편집은 사용자가 별도로 선택하고 기존 revision 조건을 요구한다.
- **삭제·한도:** 사용자가 원본 메시지/대화를 삭제해도 이미 저장된 일반 Wiki 문서는 유지한다. 아직 저장 전인 초안은 원본 삭제 뒤 저장할 수 없다. 일반 Wiki API의 제목 200자·본문 100,000자 제한과 메시지 12,000자 제한은 바꾸지 않는다. 초안 편집 뒤 Wiki 본문 제한을 초과하면 저장을 거절하고 이유를 표시한다.
- **재시도·결과 표시:** 저장 제출에는 초안별 안정적인 요청 ID와 입력 해시를 사용한다. 같은 ID·같은 입력 재전송은 이전 결과를 반환하고, 같은 ID·다른 입력은 충돌이다. 요청 기록과 문서 생성은 원자적으로 처리한다. 응답 유실/timeout은 성공으로 간주하거나 새 ID로 자동 재전송하지 않고, 같은 ID로 결과를 조회·재시도하도록 `결과 확인 필요` 상태를 표시한다. 저장 성공은 문서 ID와 revision을 보여 주며, 오류·제목 중복·revision 충돌·결과 불명 상태를 구분한다. 취소는 Wiki 쓰기를 하지 않는다.
- **신뢰성·범위:** 저장 원문은 사용자가 작성한 메시지 그대로이며, LLM이 생성한 제목/요약/답변을 사실로 승인하거나 외부 자료의 사실성을 확인한 것으로 표시하지 않는다. 문서 내 지시문은 비신뢰 데이터다. 가족 공유 Wiki가 범위이며 개인별 권한, 업로드, 어시스턴트 답변 저장 및 문서 삭제 동작은 추가하지 않는다.

### 기존 구현 경계와 후속 테스트 설계

- `begin_generation`은 채팅 요청 ID를 같은 대화·같은 본문에 묶지만, Wiki `POST /api/v1/wiki/documents`에는 저장 요청 ID가 없다. 통합 Wiki 쓰기는 caller-owned SQLite transaction과 revision 1..n을 사용하고 revision 이력은 문서별 최대 100개다. D03에서만 필요한 최소 저장 영수증/멱등성 기록을 구현한다.

- 현재 메시지는 서버에 저장된 `user` 메시지여야 하며 앞뒤 공백 제거 후 유니코드 코드 포인트 기준 1,000자 이상이다. `quick`이 아니면 기존 일반 후보를 유지한다. 직전 메시지는 같은 대화의 바로 앞 완료된 `assistant` 응답임을 호출자가 확인해야 한다. 누락·페이지 경계·실패·취소·임시 스트리밍 ID·확인 불가 시 `ordinary`로 처리한다. D06 시점의 메시지 API에는 완료 여부가 없었으나 D07에서 완료된 생성에 연결된 assistant 메시지에 한해 `generation_completed`를 제공한다. 없는 값이나 false는 강조하지 않는다.
- 직전 응답은 좁은 직접 요청 문구만 일치한다: `추가/상세/관련 정보·자료·내용`을 `알려주세요/알려주시면/제공해 주세요/주시면` 등으로 요청하거나, 영어 `please share/provide/send more/additional/further information/details/context/material` 및 `could/can/would you ...` 표현이다. 한국어 높임 표현과 영문 표현은 코드의 허용 패턴에 한정된다. 질문이나 문서 내용을 일반적으로 언급하는 것만으로는 충족하지 않는다. 직전 응답에 인용부호·코드 표시 또는 인용 줄이 있으면 강조하지 않는다. 현 사용자 본문이 코드·인용 표시로 시작하거나 물음표로 끝나도 강조하지 않는다. 이 기준은 모든 인용·명령·질문을 이해하는 자연어 판정이 아니며 애매한 사례를 놓칠 수 있다.
- 강조 제안은 자동 저장 의사나 자료 검증이 아니다. `저장 내용 확인`은 기존 원문 기반 편집·공유 안내·중복 확인 화면만 열고, 저장은 기존 최종 확인·원본 검증·멱등 요청 경로에서만 수행한다. `이번 대화에서만 사용`은 제안만 닫고 수동 진입점을 남긴다. 단일 메시지에서 일반 후보와 강조 제안을 함께 표시하지 않는다.
- 닫힘 상태는 **브라우저 메모리의 대화 ID·서버 메시지 ID 기준**으로 유지한다. 가상 스크롤·재렌더·대화 전환 후 재진입 중에는 같은 메시지 제안을 재표시하지 않는다. 새로고침·새 탭·다른 기기에서는 유지하지 않음을 안내하며, 별도 DB migration은 추가하지 않는다. 저장 성공 후에도 해당 세션에서는 다시 제안하지 않는다. 구체적인 상태 연결과 전환·네트워크 실패 처리는 D07에서 구현·검증한다.

- 따라서 D10은 자동 회귀가 통과했어도 실제 화면과 사용자 검증을 완료할 때까지 열린 상태로 유지한다. 최신 변경의 배포와 실제 운영 테스트는 별도 사용자 지시에 따른다.

## 위험과 롤백

- 긴 자료의 사실성·민감 정보는 확인 화면에서 사용자가 판단한다. 출처와 사용자 확인은 내용의 진실성을 보장하지 않는다.
- 불필요한 후보 제안과 오탐은 보수적인 감지와 메시지별 수동 진입점으로 완화한다. 실제 장문 회귀 예제와 미검출 사례를 함께 평가한다.
- 중복·동시 수정·응답 유실은 원자적 요청 기록, 결과 재조회 및 revision 조건으로 다룬다. 불명 결과에서 새 요청 ID로 자동 재시도하지 않는다.
- 문제가 생기면 후보 제안·새 저장 경로를 비활성화하거나 UI 진입점을 숨긴다. 이미 저장된 Wiki 문서·대화·기억은 삭제하지 않는다. 스키마 변경이 있는 경우 롤백 가능한 버전과 구버전 writer 통제는 배포 전에 확인한다.
